Operational notes for Claude sessions working on this repo — dense, for an
agent, not prose for an external reader (that's what README.md is for).

## What this repo is

Fork of [naumenis-code/TRASSIR-Monitor](https://github.com/naumenis-code/TRASSIR-Monitor)
(upstream, not under our control), forked 2026-09-04 specifically because
upstream shipped a `/login` page and a `login_required` decorator that was
never actually applied anywhere — every settings/server-management
mutation was reachable with zero authorization, and `GET /api/servers`
returned every TRASSIR server's SDK password in plaintext to anyone who
asked. See "Authorization hardening" and "Alert-logic audit" below for
what changed here vs. upstream. We do not have push access to upstream —
fixes land here (`scp-oss/TRASSIR-Monitor`), not there. If upstream ever
merges equivalent fixes, re-diff before assuming this fork is still ahead
on every point.

Designated branch: `main`. `git push` to this repo works directly from a
Claude Code session (confirmed 2026-09-04) — no format-patch/SendUserFile
handoff needed, unlike some other repos in this org's history.

## There is no app.py, templates/, tg_bot.py, or mail_bot.py in this repo

This is the single most important structural fact for working on this
codebase. The actual Flask application, its 5 Jinja templates, and both
notifier bots do not exist as standalone files anywhere in git — they are
generated on the target server by heredocs embedded inside three
top-level installer shell scripts, each `cat > $SOME_PATH << 'MARKER'`
blocks writing the real file at install time:

| Real file (only exists on a deployed server) | Generated by | Heredoc marker |
|---|---|---|
| `/opt/trassir-monitor/app/app.py` | `install-trassir-monitor.sh` | `APPEOF` |
| `templates/base.html` | same | `BASEEOF` |
| `templates/dashboard.html` | same | `DASHEOF` |
| `templates/server.html` | same | `SERVEREOF` |
| `templates/settings.html` | same | `SETTINGSEOF` |
| `templates/login.html` | same | `LOGINEOF` |
| `gunicorn_config.py`, systemd unit, nginx site, uninstaller | same | `GUNEOF`, `SERVEOF`, `NGINXEOF`, `UNEOF` |
| `tg_bot.py` (or `tg_proxy_bot.py`) | `install-telegram-notifier.sh` | `TGBOTEOF` |
| `mail_bot.py` | `install-mail-notifier.sh` | `MAILBOTEOF` |

**To edit application logic, edit the heredoc block inside the relevant
`.sh` file directly** — there is no separate source-of-truth file to
sync afterward, the heredoc *is* the source. To read/lint/compile-check
the embedded Python or Jinja in isolation (this session's actual workflow
for every change below), extract it first:

```bash
# app.py
awk '/^cat > \$INSTALL_DIR\/app\/app.py << .APPEOF./{flag=1; next} /^APPEOF$/{if(flag){flag=0}} flag' \
    install-trassir-monitor.sh > /tmp/app.py
python3 -m py_compile /tmp/app.py

# a template — validate with Jinja2's own parser, not just eyeballing
python3 -c "
import re, jinja2
content = open('install-trassir-monitor.sh').read()
m = re.search(r\"cat > \\\$INSTALL_DIR/templates/settings.html << 'SETTINGSEOF'\n(.*?)\nSETTINGSEOF\n\", content, re.S)
jinja2.Environment().parse(m.group(1))
"

# tg_bot.py / mail_bot.py — same idea, markers TGBOTEOF / MAILBOTEOF
sed -n '/^cat > "\$TGBOT_PY" << .TGBOTEOF./,/^TGBOTEOF$/p' install-telegram-notifier.sh | sed '1d;$d' > /tmp/tgbot.py
```

Never trust "it looks right" on a heredoc edit without doing this — a
stray heredoc-quote or indentation slip is invisible in a diff view but
breaks the generated file at install time on every future server.

## No execution access — testing is mock-based, not live

This session (and any Claude Code session working on this repo so far)
has no SSH/exec access to a real TRASSIR server or a real deployed
instance — only git. There is no way to install the app and click through
it. The verification method used for every functional change below:
extract `app.py` per the snippet above, monkey-patch its hardcoded
`BASE_DIR = "/opt/trassir-monitor"` to a temp dir, replace `TrassirClient`
with a fake that returns scripted `health`/`get_channels_info()` results,
then call `init_db()` and `collect()` directly against a real (temp-file)
SQLite DB and assert on the resulting `alerts`/`health` rows. This catches
real logic bugs (see below) that a syntax check alone never would.
`pip install flask flask-cors flask-socketio requests schedule werkzeug`
needed `--ignore-installed` in this sandbox — the base image ships a
Debian-packaged `blinker` that pip's normal uninstall-before-reinstall
path chokes on (`RECORD file not found`). `geventwebsocket` (needed only
for the real gunicorn worker class, not for import-level testing) has no
importable package under that exact name — skip it for mock testing,
`async_mode="threading"` patched in locally is enough to construct
`SocketIO` without a real gevent server.

## Authorization hardening (2026-09-04)

Upstream shipped `login_required`/`is_logged_in()` and a `/login` page,
but `login_required` was defined and never applied to any route — every
mutation was reachable anonymously. Fixed here:

- `GET /api/servers` returned every server's `sdk_password` in plaintext
  to anyone, unauthenticated — no frontend even calls this endpoint with
  GET, it was pure exposure. Now returns `has_password: true/false` only,
  and the raw password is stripped from every server dict passed to
  `index()`/`server_detail()`/`settings_page()`'s templates too (defense
  in depth — the templates never rendered it, but no reason to carry it
  into template context at all).
- `POST /api/ack/<id>` (alert acknowledgement) and `POST /test-connection`
  (arbitrary host/credential probe — an oracle for brute-forcing another
  server's SDK password) had zero session check. Both now require login;
  the "Сбросить все" button on `server.html` is now `{% if logged_in %}`
  to match.
- `admin_password` was stored and compared in plaintext (`==`). Now
  hashed with `werkzeug.security` (pbkdf2/scrypt);
  `verify_admin_password()` falls back to a constant-time plaintext
  compare so an already-deployed install with an old plaintext password
  keeps working until it's changed once through `/settings`. Never
  returned via `GET /api/settings` (even hashed) — that endpoint used to
  dump the whole `settings` table including this key.
- 5-attempts/5-minutes per-IP lockout on `/login` (in-memory — fine given
  `gunicorn_config.py` pins `workers = 1`; would need an external store if
  that ever changes).
- `app.secret_key` was `secrets.token_hex(32)` regenerated on every
  process start — every `systemctl restart` silently logged everyone out
  and made `session.permanent` pointless. Now persisted to
  `data/secret_key.txt` (mode 600), created once.

## Alert-logic audit (2026-09-04)

A full audit of `collect()`, the alert lifecycle, and both notifier bots
found four real behavioral bugs — not missing features, things the README
already claimed worked. Root-caused and fixed with a mock-based smoke
test (see "No execution access" above) before pushing, not just eyeballed:

1. **A TRASSIR server going fully unreachable never created an alert at
   all.** `collect()` only wrote to `health`/`alerts` inside
   `if health["ok"]:` — the `else` branch (server down) did nothing but
   update the live dashboard cache. This meant the entire "server down /
   server recovered" notification path already built into both bots
   (`classify_alert`'s `'сервер' + 'восстановлен'` branch,
   `calc_downtime_for_alert`'s search for `%недоступ%`/`%offline%`) was
   dead code — the event that should trigger it never existed. Fixed:
   `collect()` now inserts one `critical` "Сервер недоступен: …" alert
   per outage (deduped — not one per poll) and auto-acks it on the next
   successful poll.
2. **`cpu_critical` and `archive_critical_days` were real, editable
   `/settings` fields that `collect()` never read.** Every CPU spike or
   near-empty archive was always alerted at `warning`, never `critical`,
   regardless of the configured threshold. Fixed — critical checked
   first (archive's "critical" is a *smaller* day-count than its
   "warning", unlike CPU). Found a second bug fixing this: the code path
   that updates an already-open CPU/archive alert's text only updated
   `msg`, never `level` — an alert that escalated warning→critical while
   still open would silently keep displaying/notifying as "warning"
   until the next full close. Now updates both columns together.
3. **Downtime shown in "recovered" notifications used the wrong
   timestamp and was effectively always wrong or empty.** `alerts` had
   no column recording when a problem was actually resolved — the
   notifiers used the alert's own `ts` (its *creation* time, i.e. when
   the problem *started*) as if it were the recovery time, then searched
   for an earlier "similar" alert by text (including a
   `#\d+\s+...`-shaped regex that doesn't match this app's real
   `"Камера офлайн: <name>"` message format at all). Fixed: added
   `alerts.resolved_at` (migrated via `PRAGMA table_info` + `ALTER TABLE`
   — SQLite has no `ADD COLUMN IF NOT EXISTS`), set by every
   `collect()`/manual-ack code path that closes an alert.
   `calc_downtime_for_alert()` in both `install-telegram-notifier.sh` and
   `install-mail-notifier.sh` is now just `resolved_at - ts` on the same
   row — no text search.
4. **`retention_days` was a real, editable `/settings` field with no
   code behind it at all** — `health` grew unbounded (≈5760 rows/server/
   day at the default 15s poll interval). Added `cleanup_old_data()`
   (health: delete anything older than the threshold; alerts: only
   already-`ack=1` rows, never touches an open problem), scheduled
   hourly plus once at startup.

**Cross-file consistency trap, worth remembering before touching alert
text again:** alert message strings (`"Камера офлайн: %s"`,
`"Сервер недоступен: %s"`, `"CPU: %.1f%%"`, `"Архив: %.1f дн"`) are
matched by literal prefix/substring independently in *three* separately
embedded Python programs — `app.py`'s own open/close logic, and both
bots' `classify_alert()`/`get_new_alerts()`/`calc_downtime_for_alert()`.
Nothing shares a constant across the three heredocs (they're independent
`cat` blocks in independent `.sh` files). Changing a message format in
`app.py` without grepping both notifier installers for the old string
silently breaks recovery detection or downtime in whichever bot you
missed — this is the exact class of bug fixed in point 3 above, and nothing
would catch a fresh instance of it except another manual audit or a
mock-based test like the one already set up here.
